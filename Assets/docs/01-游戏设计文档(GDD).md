## 1. 项目一句话

**「推箱子黄金无敌至尊版」** 是 2D 推箱子游戏（PC + 移动端），提供两种模式：

- **经典模式**：标准 Sokoban 玩法，玩家单线推箱子到终点。
- **拓展模式**：在经典基础上加入「邪恶推箱人」作为对手 —— 玩家每走一步，对手沿**相反方向**执行一次同质操作（移 / 推），不能与玩家重合。

整体包装成「**奶蛙推箱手 VS 邪恶推箱人**」的轻量剧情，关卡间以短句对白过渡。

## 2. 核心玩法

### 2.1 共同规则（两模式共享）

| 项目 | 规则 |
|---|---|
| 棋盘 | 矩形网格 `W × H`，外墙和障碍物均为不可通过 |
| 玩家操作 | 按下「上 / 下 / 左 / 右」即尝试沿该方向移动一格 |
| 推箱子 | 当玩家向某方向移动且该方向紧邻一格为箱子，且箱子后一格可进入（空格 / 终点）时，箱子同向移动一格，玩家也移动一格 |
| 撞墙 / 撞障碍 | 玩家不动 |
| 撞死锁箱子 | 玩家不动 |
| 撞敌人（拓展） | 玩家不动（**双向不可重合**，v2 补） |
| 终点 | 被箱子覆盖即激活，所有终点激活 = 通关 |
| 撤销 | 任意模式下均支持逐步撤销。**回退整个世界状态** —— 玩家、敌人、所有箱子的坐标一并回到上一步（v3 已确认） |
| 重置 | 回到当前关卡初始状态 |

### 2.2 撤销与状态机

- 每一步操作入库前先存一份「世界快照」，存到撤销栈。
- **v3 确认：撤销回退的是整个世界状态** —— 玩家、敌人、所有箱子一并回退，不是只回退玩家。
- 「重做栈」在玩家产生新一步操作时清空。
- 关卡完成 / 玩家按「重置关卡」时清空两个栈。

### 2.3 胜负与计步

- **胜利**：所有箱子都覆盖在终点上。
- **失败**：拓展模式下无显式失败条件；敌人无法挤压玩家，无法让玩家死亡。胜负仅由箱子是否到位决定。
- **展示**：胜利时弹出结算面板（步数 / 撤销次数 / 用时），按钮 [下一关] [重玩] [回菜单]。

**计步规则（v3 已确认）**：

| 项 | 规则 |
|---|---|
| 计数对象 | **只计玩家的步数**，拓展模式下**不计敌人步数** |
| 什么算一步 | 玩家按下方向键且**世界状态发生变化**（玩家动了 / 敌人动了 / 推了箱子，任一即可） |
| 什么不算 | 玩家与敌人都没动（双方都撞墙 / 互顶）→ 无效输入，**不计步、不入撤销栈** |
| 撤销是否减步 | **不减**。步数是"操作次数"的诚实记录，撤销单独计数 |
| 重置 | 步数归零，撤销栈清空 |
| 展示位置 | HUD 左下常驻；结算面板大字展示 |

> **为什么撤销不减步**：如果撤销能减步，玩家可以用"反复推了又撤销"把步数刷成 0，计步就失去意义。
> 撤销次数**单独统计**并在结算展示 —— 这两个数字一起看，才能反映真实的操作效率。

## 3. 模式差异

| 维度 | 经典模式 | 拓展模式（邪恶推箱人） |
|---|---|---|
| 玩家 | ✓ | ✓ |
| 敌人 | ✗ | ✓（初始位置由关卡指定，不与玩家重合，不与箱子重合） |
| 推箱子判定 | 仅玩家推 | 玩家与敌人都会推箱子 |
| 敌移动时机 | — | **玩家每按一次方向键后**，敌人朝「玩家该步的反方向」执行一次同质操作（详见 §3.1）。<br>⚠️ v2：与玩家是否真的走成**无关**，玩家撞墙敌人照走 |
| 重合 | — | 玩家与敌人**禁止重合**（详见 §3.2） |
| 关卡验收 | 必须有解 | 必须有解；编辑时不放置敌人时退化为经典玩法 |

### 3.1 邪恶推箱人的「相反操作」语义

> 这是题目里最容易被实现歪的部分，下面把规则钉死。

**触发**：玩家按下方向 D ∈ {Up, Down, Left, Right}，敌人**无条件**尝试沿 `Opposite(D)` 移动一格。

> **关键（v2 修订）**：敌人的执行与玩家是否移动成功**完全解耦**。
> 玩家撞墙不动 ≠ 敌人不动。只要敌人在 `Opposite(D)` 方向上还能走，它就走。

**反方向**：`Opposite(D)` 映射如下：

| D | Opposite(D) |
|---|---|
| Up | Down |
| Down | Up |
| Left | Right |
| Right | Left |

**执行顺序**：先判玩家，再判敌人。**两者结果互不影响**，各自独立结算。

1. 玩家沿 `D` 尝试移动。撞墙 / 撞障碍物 / **撞敌人** / 推不动的箱子 → 玩家**不动**。
   > 「撞敌人不动」是 v2 补的对称规则：题目「无法和主角重合」是**双向**的，玩家也不能走进敌人格子。
2. 敌人沿 `Opposite(D)` 尝试移动，走与玩家**完全相同**的判定流程：
   - 前方是墙 / 障碍物 → 敌人不动
   - 前方是箱子 → 检查箱子后方，能推则推，不能推则敌人不动
   - 前方是玩家 → **整个敌人操作取消**（这保证"无法与主角重合"，玩家撞墙没走开时同样适用）
3. 结算胜负。

**四种组合与撤销栈**：

| 玩家 | 敌人 | 世界状态变化 | 撤销栈 |
|---|---|---|---|
| 移动 | 移动 | 玩家 + 敌人（+ 各自推的箱子） | ✅ 入栈 |
| 移动 | 不动 | 仅玩家（+ 箱子） | ✅ 入栈 |
| 不动 | **移动** | 仅敌人（+ 箱子） | ✅ 入栈 ← v2 新增 |
| 不动 | 不动 | 无变化 | ❌ 不入栈（视为无效输入） |

> **入栈判定**：从「玩家是否移动」改为「**世界状态是否发生变化**」。
> 撤销栈里永远只有真正改变世界的一步，不会出现"撤销一次什么都没变"的割裂感。

**战术含义**（这个改动带来的玩法深度）：玩家撞墙不再是无意义的空转 —— 它是一次**合法的、只让敌人动一步**的操作。玩家可以故意撞墙来「喂」敌人走位，这是拓展模式的核心策略点。

**走查示例**（确认规则理解一致）：

坐标 `(x, y)`，`(0,0)` 在左上。`#`=墙 `P`=玩家 `E`=敌人 `.`=空地

场景 A —— **玩家撞墙，敌人照走**（v2 核心场景）：

```text
      0 1 2 3 4
  0   # # # # #
  1   # P # . #      P=(1,1)，墙在 (2,1)
  2   # . . . #
  3   # . . E #      E=(3,3)
  4   # # # # #

玩家按 → (D = Right)

  1. 玩家 next = (2,1) → 是墙        → 玩家不动 ✗
  2. 敌人 dir  = Opposite(Right) = Left
     敌人 next = (2,3) → 空地        → 敌人移动 ✓

结果：P 仍在 (1,1)，E 从 (3,3) → (2,3)
      世界状态变化 → ✅ 入撤销栈
```

场景 B —— **两者都撞墙，视为无效输入**：

```text
      0 1 2 3 4        玩家按 → (D = Right)
  0   # # # # #
  1   # . # . #   1. 玩家 next=(2,1) 墙   → 不动 ✗
  2   # . . . #   2. 敌人 dir=Left
  3   # E . . #      敌人 next=(0,3) 墙   → 不动 ✗
  4   # # # # #
                  结果：世界无变化 → ❌ 不入栈
```

场景 C —— **玩家撞敌人，敌人也撞玩家（互相顶住）**：

```text
      0 1 2 3 4        玩家按 → (D = Right)
  0   # # # # #
  1   # . P E #   1. 玩家 next=(3,1) 是敌人 → 不动 ✗
  2   # . . . #   2. 敌人 dir=Left
  3   # . . . #      敌人 next=(2,1) 是玩家 → 不动 ✗
  4   # # # # #
                  结果：世界无变化 → ❌ 不入栈（双方互斥，谁也进不去）
```

### 3.2 敌人初始与不死锁约束

- 编辑关卡时，敌人初始格必须满足：不在墙上、不在障碍物、不与玩家重合、不与箱子重合。
- **永不重合（双向硬约束）**：由 §3.1 保证 —— 玩家不能走进敌人格，敌人不能走进玩家格，任何一方的这一步都会整体取消。
- 不做「敌人 AI 寻路」—— 它是纯机械反射，避免和「玩家操作」耦合出复杂状态机。
- **v2 新增的关卡设计约束**：由于玩家可以"撞墙喂敌人走位"，编辑拓展关卡时必须考虑 ——
  敌人可能被玩家用撞墙操作推到原本玩家推不到的位置。关卡验收（解判定）会自动覆盖这种情况，无需人工枚举。

## 4. 关卡 & 关卡编辑器

### 4.1 关卡库（内置 / 自制 / 导入）

**导入关卡集 · Microban**

| 项 | 说明 |

| 来源 | David W. Skinner《Microban》155 关（作者条款：**可自由分发，需署名**） |
| 格式 | 标准 XSB 文本（`#` 墙 `$` 箱 `*` 箱在终点 `.` 终点 `@` 玩家 `+` 玩家在终点） |
| 转换 | `.workbuddy-img/xsb2json.py`：文本首行=顶 → 写入 y-up；墙外空地泛洪填 Wall；id 补零 3 位；校验箱/终配平 |

> ⚠️ 导入集全部为经典关卡（无敌人），只在经典模式选关页出现。

### 4.2 关卡文件格式

- JSON：`Assets/Resources/Levels/{id}.json`（运行时 `Resources.LoadAll<TextAsset>("Levels")`）
- 顶层字段：`{ id, name, mode, width, height, author, source, cells: int[], playerSpawn, enemySpawn }`
  - `cells` 为**扁平数组**，语义 `cells[y * width + x]`（JsonUtility 不支持锯齿数组）
  - `source`：`""` 内置 / `"custom"` 自制 / `"imported"` 导入（v4 新增，选关分类依据）
- 单元格编码（整数枚举）见 [技术设计文档 §2.1](./02-技术设计文档(TDD).md)

### 4.3 关卡编辑器（双形态）

> 题目硬要求。v3 决定做成 **两套壳、一套核心**：Unity Editor 插件 + 游戏内编辑器。

**为什么要两套**（这不是重复劳动）：

| 形态 | 使用者 | 场景 | 独有优势 |
|---|---|---|---|
| **A · Unity Editor 插件**<br>菜单 `Window / 推箱子 / 关卡编辑器` | 策划 / 程序 | 开发期批量做关 | 直接读写工程内 JSON；接 Unity `Undo` 系统（Ctrl+Z 撤销**编辑操作**）；不打包就能测；可与 Scene 视图联动 |
| **B · 游戏内编辑器** | 玩家 / 评审 | 发布后 UGC、笔试演示 | 打包后仍可用；评审不开 Unity 也能体验「完整关卡流程」；与游戏共用同一套 UI 风格 |

> **关键约束**：两者共用 `LevelEditorCore`（纯 C# 逻辑），只换「绘制 + 输入」的壳。
> 规则、校验、解判定**只有一份实现** —— 否则两边行为迟早不一致，这是双形态最容易翻车的地方。

**布局**：
- 左 70%：可拖拽网格编辑区，单元格尺寸 64px。
- 右 30%：工具面板 + 检查器。

**默认画布**：固定 16 × 12 单元格的可编辑区域。

**工具**：

| 工具 | 鼠标行为 | 适用模式 |
|---|---|---|
| 外墙（铅笔） | 单击切换本格是否为外墙（外墙必须围成闭合环） | 两模式通用 |
| 玩家 | 单击 / **按住拖动连续放置**；全局唯一，放新位置旧位置自动清除并整盘刷新 | 两模式通用 |
| 邪恶推箱人 | 同上（唯一） | 仅拓展模式 |
| 箱子 | 单击 / 拖动连续放置 | 两模式通用 |
| 终点 | 单击 / 拖动连续放置 | 两模式通用 |
| 障碍物（单格不可推） | 单击 / 拖动连续放置；**不可穿越，与墙同类** | 两模式通用 |
| 擦除 | 单击 / 拖动擦除任何元素（含外墙，合法性由保存时校验把关） | 两模式通用 |

> **拖动连刷规则**（v4）：按住左键滑动可连续放置；**同一笔划内每格只变化一次**，停留不会反复切换。
> 单击与拖动走同一条去重路径，避免同格重复绘制产生多余撤销步骤。

**编辑约束**（实时校验，违者工具按钮亮红不可点）：

| 对象 | 不能放在 |
|---|---|
| 玩家 | 墙 / 障碍物 / 其他玩家 / 敌人 / 箱子 |
| 敌人 | 墙 / 障碍物 / 玩家 / 箱子 / 另一个敌人 |
| 箱子 | 墙 / 障碍物 / 玩家 / 敌人 / 另一个箱子（首格重叠提示） |
| 终点 | 墙 / 障碍物 |
| 外墙 | 必须构成「闭合单连通外墙」，且把所有内部元素围起来 |

**附加按钮**：

| 按钮 | 行为 | 形态 A | 形态 B |
|---|---|---|---|
| 保存关卡 | 写 JSON：**页内「关卡名称」输入框**即关卡名；id 默认派生（英文名直接用作文件名，含中文用时间戳） | ✅ 直接落工程目录 | ✅ 落 `Application.dataPath/Resources/Levels` |
| 加载关卡 | 从关卡列表选关载入 | ✅ 工程 `Resources/Levels` | ✅ 工程关卡 + 玩家自建关卡 |
| 试玩本关 | 把当前内容塞进运行时开一局（不计分）；试玩/通关后提供 **「返回编辑器」** | ✅ 直接进 Play Mode | ✅ 场景内切换 |
| 检测是否有解 | 结构校验通过后**调用真求解器**，给出 [有解(N 步) / 无解 / 超时] | ✅ | ✅ |
| 导出 / 导入 JSON | 与外部交换关卡 | ✅ 文件面板自由选路径 | ⚠️ 仅能读同目录文件 |

> **v4 补充**：保存后立即重扫关卡目录，回到选关页即可看到新关卡（无需重启）；
> 试玩对局在**暂停页与结算页**额外出现「返回编辑器」按钮（正常游玩关卡时不显示）。

**形态差异（只有这些，逻辑全共用）**：

| 维度 | A · Editor 插件 | B · 游戏内 |
|---|---|---|
| 绘制方式 | `EditorWindow` + UIElements / IMGUI | uGUI（由 UI Builder 产出 prefab） |
| 撤销编辑操作 | Unity `Undo.RecordObject` + Ctrl+Z | 自建编辑操作栈 |
| 文件读写 | `File` API 直写工程 | `File` API（编辑器）+ `persistentDataPath`（运行时） |
| 画布渲染 | 纯 IMGUI 绘制格子色块 | 与游戏共用 Sprite 渲染，所见即所得 |

### 4.4 解判定（点击「检测是否有解」）

> 求解器是题目之外的产品加分项，但作为技术策划必须把握"做什么 vs 不做什么"的边界。详见 [02-技术设计文档 §4](./02-技术设计文档(TDD).md)。
>
> v3 决定采用**正向 BFS 与反向 BFS 混合**策略，按箱子数自动切换，以覆盖更大的关卡规模。
>
> **v4 实测结论**：
> - 「校验」按钮 = **结构校验 + 真求解器**两段。仅结构合法（箱终配平、外墙闭合、对象合法）不足以说明有解。
> - 求解器**复用运行时同一套 `SokobanRules.Step`**，因此障碍 = 不可通行、箱子推动规则与游玩完全一致，不会"假装可解"。
> - 编辑器内超时设为 **3s**，结果三态明确：
>   - `有解（约 N 步）` —— BFS 找到最短解；
>   - `无解` —— 状态空间穷尽或初始/推入死格；
>   - `超时` —— 关卡较大，**如实告知"暂不能确定"**，不假装有结果。
> - UX：点击按钮 → 状态栏直接出结论（无异步，3s 内同步返回）。若超时，提示玩家缩小关卡或减少箱子数。

```
   ▼                ▼                                  ▼
[游戏中] ←——————┘                              [暂停 / 结算]
   │ [暂停] / [撤销] / [重置]
   ▼
[结算]
```

- **游戏中 HUD**：左下步数 / 撤销次数 / 用时；右上 [暂停] [重置] [撤销] [重做] [菜单]。
- **调试入口（仅 Editor）**：`Window / 推箱子 / 关卡编辑器` 可直接打开编辑器插件形态。
- **平台适配（v3 新增）**：PC + 移动端双端支持，详见 §5.1。

**选关页（v4 增强）**：关卡数量上百后单页滚动不可用，改为：

| 能力 | 说明 |
|---|---|
| **分类标签** | 全部 / 内置 / 自制 / 导入（`LevelData.source` 驱动，选中态烫金高亮） |
| **搜索** | 输入框按 **关卡名 / ID / 作者** 子串实时过滤（大小写不敏感），输入后重置到第 1 页 |
| **分页** | 每页 5 关，底部 [上一页] [第 X / Y 页] [下一页]；翻页时按全局下标重绑点击 |
| **即时刷新** | 每次进入选关都重扫 `Resources/Levels`，编辑器刚保存的关卡立即可见 |

### 5.1 平台与屏幕适配

> 题目只要求 PC，但 v3 决定顺带做移动端 —— 因为 UI 走 UI Builder 产出，多分辨率适配是**工具自带的能力**（9:16 / 9:19.5 / 9:21 / 16:9 比例预览），边际成本很低。

**支持的形态**：

| 平台 | 比例范围 | 输入方式 |
|---|---|---|
| PC（主） | 16:9 / 16:10 / 21:9 | 键盘方向键 / WASD；手柄十字键 |
| 移动端竖屏 | 9:16 ~ 9:21 | 滑动手势（四方向）+ 屏幕按钮 |
| 移动端横屏 | 16:9 ~ 21:9 | 同上，HUD 改为左右分布 |

**适配规则**：

1. **棋盘优先**：棋盘始终整体等比缩放并居中，保证**任何比例下棋盘都完整可见**，不被裁切、不被拉伸变形。
2. **HUD 贴边**：HUD / 按钮用锚点贴边（左上 / 右上 / 左下 / 右下），不用绝对坐标，比例变化时自动跟随。
3. **刘海与圆角**：移动端套 SafeArea，避开刘海、挖孔、Home 指示条。
4. **竖屏布局**：棋盘占上 60%，操作区（滑动区 / 按钮）占下 40%，拇指可达。
5. **横屏布局**：棋盘居中，HUD 分列左右两侧。
6. **字号**：随 `CanvasScaler` 的 `Match Width Or Height` 缩放，竖屏 match=Width、横屏 match=Height。

> **移动端不做的事**：不做账号、不做内购、不做触屏长按连续移动（一次滑动 = 一步，避免误触连走）。
